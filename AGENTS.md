# Agent instructions

This repository's quality gate is the `quality` command-line tool in
[`tools/quality`](tools/quality/README.md), from the AI boilerplate template.
Hooks and CI only call it; a pass or fail comes from the tool, not from the
wrapper.

## Setup

```sh
./quality bootstrap
```

Bootstrap installs the pinned tools, fills the package caches, and installs
the check-only `pre-commit` hook (add `--pre-push` for the push hook). Run it
again after pulling changes to `tools/quality` or a lockfile, and after
staging a new component; `./quality doctor` says whether everything is ready.
Bootstrap sets up only the profiles the staged components use. Prerequisites
are in [decision 0002](docs/decisions/0002-installation-strategy.md).

## Components

- `./quality component add <directory>` adds a directory with a supported
  manifest to `quality.toml`; stage both, run `./quality bootstrap`, and
  commit. The [profile support matrix](docs/reference/profiles.md) lists the
  manifests and layouts.
- New languages and coverage formats are added as described in the
  [extension guide](docs/guides/extending.md).
- `./quality tools update <tool> <version>` moves a pinned tool to another
  release with the vendor's checksums; the
  [maintenance guide](docs/guides/maintenance.md) covers updating tools,
  packages, policy, and the template.

## Checks

- `./quality check` checks the staged candidate in an isolated snapshot; the
  pre-commit hook runs exactly this. Stage your changes first, because
  unstaged and untracked files are ignored.
- `./quality check --rev HEAD` checks a commit; `--all` covers every active
  component instead of the affected ones.
- `./quality fix` applies safe formatter and lint fixes to the working tree.
  It never stages anything: review the change and stage it yourself.
- `./quality test` runs the unit suites of the affected components with their
  coverage floors; `--suite`, `--component`, and `--all` select more.
- `./quality self-test --level unit` or `--level e2e` tests the quality
  tooling itself.

- `./quality scenarios` validates the scenario manifests without running
  tests and suggests undeclared capabilities
  ([decision 0014](docs/decisions/0014-behavioral-scenarios.md)).
- `./quality explain <rule-id>` explains a finding and its fix.
- `./quality links` probes external links in the documentation. It needs the
  network and is not part of `./quality check`.
- `./quality gate` and `./quality audit` are what CI runs; a pull request
  passes only when the `required` job of the
  [quality workflow](.github/workflows/quality.yml) succeeds
  ([decision 0015](docs/decisions/0015-ci-wrappers-and-merge-gates.md)).
  Changes to control files need code-owner review.
- `./quality policy validate` validates [`quality.toml`](quality.toml).
- Every command and exit code is listed in the
  [command-line reference](docs/reference/cli.md).
- Native commands for working on the core itself are in the
  [core README](tools/quality/README.md#native-development-commands).
- Never bypass the hooks with `--no-verify`; fix the finding instead.

## Boundaries

- [`quality.toml`](quality.toml) is the only place for thresholds, components,
  classification, and exceptions. Link to it; do not copy its values.
- Core packages depend only on lower layers
  ([decision 0003](docs/decisions/0003-architecture.md)); the layers are
  declared in `quality.toml` and enforced by `quality check`.
- `docs/reference/policy.schema.json` and `scenarios.schema.json` are
  generated by `quality policy schema --write`; never edit them by hand.
- Write documentation and comments in English. Keep every page linked from
  the [documentation index](docs/README.md).

## Exceptions

Fix the finding first. When an exception is justified, add an
`[[exceptions]]` entry to `quality.toml` with the rule ID, the exact path, the
symbol (for an inline marker, its text from the marker on), a reason, an
owner, and `expires` for a temporary or `review` for a permanent exception.
Expired and unused exceptions fail the check; rules about the policy, Git,
discovery, secrets, tests, coverage, scenarios, quarantine, and exceptions
themselves cannot be excepted. Details are in
[decision 0007](docs/decisions/0007-common-gates.md).
